breakdown

The one-shot prompt expander. One rough sentence in — a fully engineered, ready-to-run plan out.

Where /promper engineers a single prompt, breakdown engineers the whole run — it interviews you, writes the spec, splits the job into the right pieces, staffs each piece with a specialist, and hands back a plan. Nothing runs until you say go.

$ /promper:breakdown migrate the billing service to event sourcing
In plain terms

You describe what you want built — in a sentence. breakdown does the planning a senior engineer would do before writing any code.

It asks a few sharp questions, turns your answers into a proper written spec, and figures out which parts of the work are frontend, backend, database, testing, and so on.

Each part is then handed to the right specialist persona — not a generic "you are an expert" — and packaged as a clean, self-contained instruction. You get the map before anyone starts driving.

The pipeline

From one line to a staffed plan, in six moves.

Every step is deliberate. The steps that decide what the work is are deterministic — same input, same breakdown, no dice-rolling.

01

A short requirements interview

Questions come in one batch, not a drip. Your answers become a tailored PRD — a product-requirements document written for you. Already have a spec? Feed it in with --prd.

02

It splits the work into domains

promper classify reads the PRD and cuts it into domain nodes — pieces of work like "API", "data model", "tests". This runs on fixed trigger tables with zero AI, so it's fast, free, and repeatable.

03

It files the work as a tracked graph

Using Beads, breakdown creates an epic plus one issue per node, wired with the dependencies between them. Opt-in and non-blocking — skip it with --no-beads, and everything still works if Beads isn't installed.

04

Each node inherits a specialist

Every node is routed to the specialist agent whose job it is — and it borrows that agent's real persona and toolkit, rather than inventing one. This is where Lean CTX prescriptions get folded in, telling each specialist what to read and how to read it leanly.

05

Every node ships as one engineered prompt

Each piece becomes a single, clean Claude-native prompt — role, context, instructions, constraints, output format, all filled in. Need portable or non-Claude prompts instead? --target=costar.

06

You get a plan — and nothing spawns

breakdown presents a parallel-lane execution plan — what can run at once, what waits on what — and then stops. Add --run to execute, deciding per node whether to run it inline or hand it to a subagent.

What you keep

Everything lands on disk as real files.

No black box. The whole run is written into a project folder you can read, edit, version, and hand to anyone — spec, dependency graph, plan, and one prompt per piece of work.

.promper/<slug>/
├─ PRD.md the written spec
├─ graph.json nodes + dependencies
├─ plan.md parallel-lane plan
└─ prompts/ one per node
The dependencies, up close

breakdown stands on two shoulders.

Neither is required to try it — both are optional, and breakdown degrades gracefully without them. But when they're present, they're what makes the output feel like a real engineering plan instead of a to-do list.

Beads bd the memory & issue tracker built for coding agents
What it is

A lightweight, git-native issue tracker for AI agents. Instead of losing plans in scattered markdown, Beads stores work as a dependency-aware graph — epics, tasks, and the links between them — so an agent can pick up long jobs across sessions without forgetting where it was.

Its signature move: bd ready surfaces only the work that isn't blocked — a live queue that respects the plan's order.

What it does here

When breakdown finishes decomposing your request, it files the run into Beads: one epic, one issue per node, with every dependency wired in.

Your plan stops being a static document and becomes a queryable work graph — the agent can ask "what's ready?" and always get the right next piece. It's opt-in and never blocks the rest of the pipeline.

Lean CTX lean-ctx the context layer that decides what an agent reads
What it is

A single local tool that governs the context between your code and the AI — deciding what it reads and compressing what it sends, often cutting token use by more than half.

The point isn't only cheaper. As a window fills with noise, a model's accuracy drops — so trimming to the highest-signal lines keeps the agent sharper, not just leaner.

What it does here

When Lean CTX is present, breakdown reads its prescriptions and folds them into each node's prompt — so every specialist arrives already told which files and context to pull, and to pull them leanly.

A node doesn't just know who it is; it knows what to look at before it starts — no wandering, no wasted window.

Beads is created by Steve Yegge (steveyegge/beads). Lean CTX is yvgude/lean-ctx. Both are independent open-source projects; breakdown integrates with them but ships without either.

Why it matters

Agentic engineering, shipped as a package — not a whiteboard idea.

Plan-first

It thinks through the entire job before a single agent runs. You review the plan, then choose to execute.

Deterministic where it counts

Deciding what the work is uses fixed tables, no AI — so the same request always breaks down the same way.

Every piece is staffed

Each node carries a real specialist persona and its toolkit — engineered prompts, not "you are an expert."

Most "agentic planning" lives in blog posts and demos. breakdown is the same discipline compiled down to one command: interview, spec, split, staff, prompt, plan. It runs on Claude Code and Codex alike, leans on no single hook, and states how every phase degrades if a dependency is missing.
